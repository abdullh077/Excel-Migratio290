---
name: Visa manager offline sync architecture
description: How offline read/write is layered under fetch for Umrah, Visas, and Statement pages; the multi-tenant outbox-scoping rule; the client-list identity gotcha.
---
- Offline read/write for the daily-work pages is a drop-in fetch wrapper (network-first, IndexedDB-cache fallback on read; network-first with local queue-and-optimistic-patch on write failure) layered under the existing pages — pages did not need to be rewritten to a different data-fetching model.
- **Multi-tenant rule (hard requirement, caused a rejected review once):** the local write queue is shared IndexedDB storage across every office that has ever logged into this device/browser. Any queue-replay or pending-count logic MUST filter to the currently authenticated office's records only. Never replay, count, or surface a queued write belonging to a different office than the one currently signed in — a device switching accounts would otherwise submit writes under the wrong tenant.
  - **Why:** the cache/queue store doesn't get wiped on logout (so a legitimate reconnect-later flow isn't lost); it's scoped instead by comparing each record's stored office id against the currently authenticated office id at the moment of read/replay.
  - **How to apply:** anywhere new code reads or replays local queued/cached data, scope the query by current office id — don't assume "everything in the local store belongs to me."
- **Client-list identity gotcha:** some derived list resources (e.g. a "clients" list built from transactions + an optional manual account row) have no stable numeric id — they're identified by name instead, with an optional secondary numeric id only for records that also have a manual account. Generic "match cached row by `.id`" patch logic silently no-ops for these; such resources need an explicit alternate match key (e.g. by name for renames, by the secondary id for deletes).
- Found and fixed an unrelated pre-existing bug while building this: a DB table existed in the ORM schema but was never migrated into the actual database, so a feature using it failed with "relation does not exist". Lesson: that error means check migration state, not necessarily that the code is wrong.
